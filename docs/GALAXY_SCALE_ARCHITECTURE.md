# Galaxy Scale — Architecture Research (Phase 4 / Variant C)

Документ — **исследование**, а не реализация. Цель Phase 4: определить архитектуру,
позволяющую процедурной галактике содержать **большое количество планет**, не заводя
отдельный Minecraft Dimension на каждую потенциальную планету.

> Phase 3 (Variant A, `test_planet`) остаётся рабочим baseline. Этот документ НИЧЕГО не
> ломает и ничего не реализует; это анализ + рекомендация.

---

## 1. Problem statement

### Желаемая концепция
```
Galaxy
 |-- StarSystem
 |    |-- Planet  (PlanetDefinition)
 |    |-- Planet
 |    `-- Planet
 |-- StarSystem
 |    `-- ...
 `-- ...
```
- `PlanetDefinition` — **детерминированные чистые данные** (id, seed, system, orbit, type).
  Их количество потенциально **большое / почти неограниченное** (вычисляются по сиду лениво).
- Minecraft `Dimension` **не должен масштабироваться 1:1** с количеством `PlanetDefinition`.

### Итого, что нужно решить
1. Как представить «планету, на которую можно попасть» в MC, если измерений мало/одно.
2. Мультиплеер: A-B-C одновременно на разных планетах.
3. Persistence после рестарта и обновления мода.
4. Совместимость с Creating Space (ракеты/телепорт).
5. НЕ использовать Mixin/Reflection/AT «в обход».

## 2. Phase 3 baseline (что уже есть и НЕ трогаем)

- `core.planets.PlanetDefinition / PlanetProperties` — чистая детерминированная модель.
- `core.worldgen.PlanetWorldgenProfile` — чистый маппинг свойств -> профиль (без MC).
- `core.worldgen.terrain.TerrainGenerator` — чистая функция `seed + x + z -> height`.
- `worldgen.planet.PlanetChunkGenerator / PlanetBiomeSource` — MC-конец конвейера.
- `worldgen.planet.PlanetDimensionBinding` — отделяет `PlanetDefinition` от `ResourceLocation`.
- Одно pre-registered измерение `unlimitedspace:test_planet` (Variant A POC).
- Правило зависимости: `core/*` не знает о Minecraft (проверяется `CoreArchitectureTest`).

**Ключевой факт (базис анализа):** в NeoForge 1.21.1 измерение (`ServerLevel`) создаётся
только на bootstrap из записей `Registries.LEVEL_STEM` (datapack). После
`MinecraftServer.createLevels()` добавить `ServerLevel` в рантайме **публичного API нет**.
`ChunkGenerator` запекается в `LevelStem` при создании мира и **неизменен** на весь срок
жизни `ServerLevel`.

## 3. Variant A — pre-registered dimensions (1 dimension = 1 planet, static)

### Диаграмма
```
Galaxy (data, N PlanetDefinition, ленивые)
   | выбор планеты
   v
PlanetDefinition -- PlanetDimensionBinding --> ResourceKey<LevelStem>   (datapack JSON)
                                                | создаётся на bootstrap (createLevels)
                                                v
                                  ServerLevel (свой каталог chunks, свой save)
```
- Каждая «доступная» планета объявлена datapack-записью (`dimension_type` + `dimension`).
- N измерений = N планет.

### Свойства
| Параметр | Значение |
|---|---|
| Макс. планет | ограничено числом pre-registered LevelStem |
| Одновременно активные | любое число из предзарегистрированных |
| Persistence | vanilla save per dimension |
| Restart | да, stable seed (генератор декодится из JSON) |
| Multiplayer | да, если измерение предзарегистрировано |
| Создание | статично (datapack/datagen); добавить планету = добавить JSON + рестарт |
| Совместимость CS | **отличная** (CS ожидает dimension-на-планету) |
| Mixin | нет |

### Ограничения
- Количество «играбельных» планет = числу заранее объявленных измерений (не «неограничено»).
- Сотни измерений реалòn; тысячи — дорого (см. Performance).
- Нельзя создать новое измерение во время игры (только datapack + рестарт).

## 4. Variant B — runtime dimensions (Mixin/Reflection) — ЗАПРЕЩЁН

Переопределение внутренних мап `ServerLevel`, инъекция `ServerLevel` в рантайме.
- Публичного API нет; возможно только Mixin/Reflection/AT на `MinecraftServer.levels`,
  `ServerLevel`/`ChunkMap`.
- **Вердикт: запрещён политикой проекта.** Любой вариант, требующий этого, признаётся
  нереализуемым в рамках ограничений и фиксируется как ограничение.

## 5. Variant C — reusable dimension pool (ПОД ВОПРОСОМ — исследовано)

Концепция: «ограниченный пул измерений; измерение переиспользуется для разных планет».
Ключевой вопрос: **можно ли поменять планеты, которые представляет `ChunkGenerator`?**

### Анализ жизнеспособности

**Факт 1.** `ChunkGenerator` привязан к `LevelStem` и создаётся ОДИН раз при создании
`ServerLevel` (из datapack-кодека). У одного `ServerLevel` **всегда один и тот же**
`ChunkGenerator`, один `biomeSource`, одно мировое время, один мировой бордер, один каталог
chunk-хранения, одни `LevelTicks`/block entities/entities.

**Факт 2.** Чтобы один `Dimension X` представлял «сейчас Planet A, а позже Planet B», нужно
либо:
- (2a) заменить `ChunkGenerator`/`biomeSource` в уже созданном `ServerLevel` -> **мутации
  внутренностей -> запрещено (по сути это Variant B-lite)**;
- (2b) полностью выгрузить/стереть/пересоздать `ServerLevel` под новую планету -> тоже
  требует доступа к `createLevels`/`levels`-карте в рантайме -> запрещено;
- (2c) держать состояние нескольких планет в ОДНОМ мире через координаты (регионы) —
  но это уже **Variant D**, а не «переиспользование измерения».

**Факт 3 (главное ограничение).** Если одно измерение представляет ровно одну планету в
конкретный момент, а два игрока одновременно на разных планетах — для второго нужно либо
второе измерение, либо перезапись первого (что сломает первого). **Значит «один Dimension =
одна актуальная планета на момент времени» при мультиплеере требует, по сути, разнесения
планет по координатам в одном измерении, т.е. это Variant D.**

**Вердикт по Variant C:**
- Как «переключение планеты в рамках одного измерения на лету» — **НЕ жизнеспособен**
  без запрещённого рантайм-мутирования ServerLevel.
- Как «небольшой пул измерений, каждое статически прибито к своей планете» — это частный
  случай **Variant A** (ограничен N).
- Как «пул = несколько планет на одно измерение через регионы» — это **Variant D**.

> **Фиксируем ограничение:** нет честного способа «переиспользовать» ServerLevel для
> смены планеты во **времени** без серверной магии. Единственные честные русла:
> (1) статическая привязка «измерение = планета» (A), либо (2) планет много, но они —
> **регионы** внутри одного/нескольких измерений (D).

## 6. Variant D — один dimension как (огромная) виртуальная карта космоса

### Диаграмма
```
Minecraft Dimension: unlimitedspace:space   (один ServerLevel)
   +--------------------------------------------------------------+
   |  system 0 / planet 1 (cell region)   system 1 / planet 0     |
   |        [PlanetProperties->TerrainGenerator]                   |
   |         вне планет — пустота/космос                          |
   |        system 3 / planet 2   (игрок A и C здесь)              |
   |                         . игрок B system 48/planet 7         |
   +--------------------------------------------------------------+
Кастомный ChunkGenerator по (x,z) определяет: «какая планета» -> берёт её сид ->
генерирует рельеф ТОЛЬКО в пределах её круга; всё остальное — пустота (космос).
```

### Что это даёт
- Планет **сколько угодно** — идентичность кодируется координатой региона (без отдельных
  измерений). `PlanetDefinition` остаются чистыми данными, их число не ограничено.
- Мультиплеер A/B/C — рядом/на разных регионах одного мира -> работает нативно.
- Persistence/restart — vanilla save одного измерения.
- `core/* -> TerrainGenerator` конвейер не меняется: генератор получает сид планеты из (x,z).
- Нет `ServerLevel` на планету -> нет раскрутки N измерений, нет нагрузки на save от N каталогов.

### Ограничения (честно)
| Аспект | Что происходит | Насколько критично |
|---|---|---|
| Мировое время | одно `DimensionType` = одно `fixedTime`/длина суток для всего измерения | Планеты одной звёздной системы физически делят длину суток — приемлемо; нельзя разным планетам задать разную длину дня (только общий `fixedTime`) |
| Мировой бордер | ОДИН бордер на измерение (per-planet border не нативно) | Отключить/огромный бордер; ограничивать планету через рельеф/космос |
| Структуры | structure placement глобальный на измерение (нет «per-planet structures») | Для кастомных планетных структур нужен свой генерационный шаг или отказ от структур (POC их не имеет) |
| Расстояния | межпланетные расстояния реальные -> много «пустых» цепочков космоса | Ленивая генерация по движению; пустые чанки почти бесплатны |
| Клиент | один dimension effects/небо на всё | Ограничение эстетики (или свой renderer) |
| Teleport | смена планеты = телепорт внутри того же мира (позиция-регион) | Проще, чем порталы между измерениями |

## 7. Alternative E — прочие (без реализации)

- **E1 «Только данные, измерения только для «посещаемых»».**
  Галактика = чистые данные (неограниченно). MC-измерения создаются **только под
  небольшой курируемый набор** планет (до ~10-…) по Variant A. Идея «материализуй то,
  что реально станет целью ракеты». **Жизнеспособна**, но не даёт «много одновременно
  играбельных планет».
- **E2 «Несколько space-измерений, каждое = звёздная система (D*)». Гибрид D: не один
  огромный мир, а по одному измерению на звёздную систему, планеты — регионы внутри
  системы. Умеренный масштаб систем, лучше бремя save. **Жизнеспособна**.
- **E3 «Custom Minecraft WorldProvider/Portal с подменой сида»** — не существует в 1.21.1
  без запрещённых хуков. Отбрасывается.

## 8. Multiplayer analysis (критично)

Сценарий:
- Player A: System 3 -> Planet 2
- Player B: System 48 -> Planet 7
- Player C: System 3 -> Planet 2

| Вариант | A и C на одной планете | B на другой | Одновременно | Вердикт |
|---|---|---|---|---|
| **A** (планеты — измерения) | same dimension -> видят друг друга | другой dimension | да, если оба измерения предзарегистрированы | можно, но только для предзарегистрированных |
| **B** (runtime) | запрещено | запрещено | — | нельзя |
| **C** (reuse пул) | нечестно (перезапись мира) | нечестно | нельзя (без серверной магии) | нельзя «как reuse» |
| **D** (регионы) | same region -> видят друг друга | другой регион | да, неограниченно | можно |
| **E1** (курируемый набор A) | можно (если Planet 2 из набора) | только если Planet 7 из набора | частично | частично |

**Вывод:** только **D** честно и неограниченно удовлетворяет мультиплеерному сценарию
без ограничения количества. **A** удовлетворяет, но лишь для предзарегистрированного
множества.

## 9. Persistence analysis (источник истины)

```
PlanetSeed --(Seeds)-> TerrainSeed -> PlanetProperties -> PlanetWorldgenProfile -> TerrainGenerator -> ChunkData (derived)
      ^
 источник истины (детерминированная идентичность)
Minecraft save = РЕЗУЛЬТИРУЮЩИЙ кэш, воспроизводимый из сида
```

### Ответы
- **Источник истины — `PlanetDefinition`/`PlanetSeed` (+ детерминированный конвейер).**
  Minecraft chunk-data — вторичная материализация.
- Рестарт: генератор декодируется из datapack (A) либо из (x,z)->сид (D); terrain
  воспроизводим из `TerrainSeed` -> стабилен.
- Обновление мода: если **алгоритм генератора меняется**, старые чанки не перегенерятся
  автоматически (vanilla). Нужна **версия worldgen** (`worldgenVersion`), вшитая в
  `PlanetWorldgenProfile`/`PlanetChunkGenerator`, чтобы решить: регенерировать или мигрировать.
- Привязка «планета -> измерение» (A) должна быть **стабильной/версионированной**, иначе
  смена бидинга = старые чанки чужой планеты. В **D** привязка «(x,z)-регион -> планета»
  жёстко детерминирована и стабильна сама собой.
- **Правило:** не хранить ничего, что нельзя восстановить из сида; любые изменения генерации
  — через versioned worldgen, не через перезапись save.

## 10. Performance analysis

| Фактор | A (измерение на планету) | D (регионы в одном измерении) |
|---|---|---|
| Число ServerLevel | = числу планет в наборе | 1 |
| Память (пустых уровней) | каждый `ServerLevel`+`ChunkMap`+`RandomState` (МБты) | ~1 x (дороже за целым регион) |
| Startup | createLevels создаёт все измерения | 1 измерение |
| Save | дамп всех dirty-центров всех измерений | дамп dirty-части посещённых регионов |
| CPU тиков | растёт с загруженными чанками (игроки) | то же, но в одном мире |
| Chunk generation | по мере посещения измерений | по мере движения; пустой космос лёгок |
| Оценка масштаба | десятки–низкие сотни комфортно; тысячи тяжело | практически неограниченно (лимит — координатное пространство/посещаемость) |

## 11. Creating Space compatibility

CS-модель полёта построена на **dimension-пер-планета**:
`RocketContraptionEntity.destination` -> `CSDimensionUtil.getPlanets()` (datapack-реестр
`rocket_accessible_dimension`) -> `ServerLevel.getLevel(key)` -> `changeDimension(переход)`.

| Вариант | Совместимость CS | Пояснение |
|---|---|---|
| **A** | из коробки | планета = dimension key; добавляем записи в `rocket_accessible_dimension` + JSON dimension |
| **B** | нельзя | запрещено |
| **C** | нельзя «как reuse» | нет честного способа |
| **D** | требует собственный integration | планета — регион; `getLevel(key)` не подходит. Нужен addon-мост: перехватывать выбор destination и делать **внутримировой** телепорт в регион (CS НЕ меняем — это наш addon-слой) |

Для **D** интеграция с ракетами CS не «из коробки»; это отдельный таск (travel bridge), но
без изменения кода CS.

## 12. Рекомендации

### Главный вывод
- **Variant C в форме «переиспользовать одно измерение для смены планеты во времени»
  НЕ жизнеспособен** без запрещённого мутирования `ServerLevel`. Фиксируем как ограничение.
- Честные жизнеспособные пути: **A** (статическое «измерение = планета», ограничено) и
  **D** (планеты = регионы в одном/нескольких пространствах, неограниченно).

### Рекомендация фазы (для подтверждения, НЕ реализация)
1. **Не отказываемся от Phase-3 Variant A `test_planet`** (baseline остаётся).
2. **Долгосрочная цель масштаба — Variant D**:
   `unlimitedspace:space` — единое пространственное измерение; планета выбирается по (x,z)
   региона; конвейер `PlanetProperties->Profile->TerrainGenerator` не меняется; мультиплеер и
   persistence на уровне vanilla.
3. **Интеграция CS — addon-side travel bridge** (CS не трогаем) либо, если жёстко нужен
   «из коробки» CS-полёт — остаёмся на **A с курируемым набором** (~8–32 планеты).
4. Ввести **worldgenVersion** для честной миграции при обновлении генератора.
